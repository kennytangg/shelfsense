# Vercel deployment

Deploy the repository root as one Next.js project with Node 24. Use a managed PostgreSQL pooled endpoint and a **private** Vercel Blob store. Preview/test environments must use separate databases and Blob stores from production. Set server-only `DATABASE_URL`, `BLOB_READ_WRITE_TOKEN`, `UPLOAD_SIGNING_SECRET`, `OPERATOR_USERNAME`, and `OPERATOR_PASSWORD`. Generate strong random signing/operator secrets. Do not expose them through `NEXT_PUBLIC_*` variables. Operator access fails closed if hosted credentials are absent.

The API uses Node runtime and a 60-second function duration. Current [Vercel limits](https://vercel.com/docs/functions/limitations) include a 250 MB uncompressed function bundle, 2 GB Hobby memory, and a 4.5 MB function request/response payload limit. Media responses stream from private storage, avoiding the buffered response limit as described in [Vercel’s streaming guidance](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions). Images use [direct client uploads](https://vercel.com/docs/vercel-blob/client-upload) to bypass that payload limit. The server independently enforces the existing 10 MiB encoded and 20-million decoded-pixel limits. Local measurements and traced bundle size are recorded in verification documentation; these are not a substitute for a hosted preview.

1. Provision an isolated preview database and private Blob store. Configure operator access and secrets, then run `npm run migrate` and `npm run initialize` explicitly against the preview database in the release environment.
2. Build/deploy a Vercel preview. Verify authenticated health, direct PNG/JPEG uploads, large-image rejection, shelf setup, stock-only checks, historical media/placement reads, restocking actions, retries and concurrency. Verify the actual function bundle, memory and duration on your plan. No deployment has been performed from this workspace because hosted credentials/configuration are unavailable.
3. For first production deployment, provision a fresh production database and private Blob store, configure credentials, then explicitly run `npm run migrate`. Run `npm run initialize` to create or reuse the shared store without samples. Before later releases, pause writes and back up database and media together with `npm run backup -- /safe/backup-directory`.
4. To transfer existing data created by this application, restore its database backup into a separate target and supply that PostgreSQL URL and Blob token locally, then run `npm run migrate:media -- --apply` with access to the backed-up media directory. It verifies byte sizes and copied SHA-256 hashes before updating asset storage keys. Keep original local images. Confirm all asset counts and hashes, domain row counts, calibration versions, history, ownership and ingestion receipts.
5. Deploy the verified application and enable operator traffic. Point optional Node folder uploaders to the new authenticated URL. Schedule `npm run storage:cleanup -- --apply` in an operator maintenance environment after reviewing its dry run.
6. For rollback, pause new writes first, back up the new database/media, and account for any post-cutover writes before restoring the old snapshot. Restore the matching database and media snapshot together. Reverting code alone does not reconcile newly written data.

Production migration execution belongs in the release workflow, not request handlers or every Vercel function startup. Hosted database/media transfer, preview verification, and production deployment are intentionally pending until provider access and target resources exist.
